How Draken

01

One app.
Clear responsibilities.

The browser handles the interface and microphone. One Node.js server owns records, checks requests and starts model work. SQLite keeps the durable history.

“Read-only” means read-only toward your coding work. Draken still writes its own database when you start a sync, talk, save notes or explicitly mark evidence reviewed.

Why one server? A kernel-backed lock enforces one owner per data directory before initialization or recovery. Jobs and calls have process-local leases; shutdown retains directory ownership until resource exit is confirmed. The tray’s separate heartbeat is discovery/presentation, not server authority. See ownership and shutdown. This remains a personal tool, not a distributed multi-user service.

02

From a click
to a conversation.

The ordinary path is Sync with Draken → prepared snapshot → call. It creates one coherent conversation, not a set of artificial user-facing batches.

  1. 01Scan

    Read complete new records from eligible local session files.

  2. 02Freeze

    Freeze membership and verified source pointers in a new snapshot.

  3. 03Prepare

    Make short prior-sync memory, then the new briefing.

  4. 04Talk

    Start the call only from the still-valid browser action.

  5. 05Remember

    Keep the exchange and request a short recap on call-UI closure.

Home stays compact

History cards help you recognize earlier conversations. Each /syncs/:id page keeps the full briefing, notes, discussion and expandable sources.

Failure does not erase work

If preparation fails or is cancelled, the snapshot and valid cached summaries stay. Foreground recovery requires an explicit retry; enabled automatic preparation has its own saved resumption policy.

A URL is not microphone permission. Call-start intent exists only in browser memory. Reloading or sharing a sync URL cannot start capture. A hidden page, denied permission or failed preparation requires explicit recovery.
Under the button: request IDs, background work and progress

POST /api/syncs/start-call receives a unique request ID. Repeating the same ID returns the same sync rather than making duplicates.

The server responds with 202 Accepted after launching preparation. That means “work accepted,” not “briefing finished.” The browser polls progress. The request itself cannot open a microphone; the browser controller performs call setup separately when preparation is ready and its original intent is still valid.

Why separate preparation from capture? A briefing can take minutes. The browser should not need one long HTTP request, and an old tab should never act as a standing instruction to record.

03

Included is
not reviewed.

The local index can change as new activity arrives. A snapshot fixes evidence membership and projection for a particular conversation; excerpts require the verified originals. Several snapshots can stay open at once.

Another open sync is a reservation

Sync B skips entries held by open Sync A. You do not have to approve A just to start a fresh conversation about later work.

Discard releases, not erases

Discarding releases held entries if they are still eligible and unreviewed. The discarded sync’s history remains readable.

StateWhat it actually means
IndexedThe collector read an entry into the local index.
AvailableEligible, not covered, and not held by another open snapshot.
IncludedA fixed snapshot contains a verified pointer and frozen projection for that evidence.
ProcessedThe entry passed through a successful first-level summary. This is not review.
ReviewedYou explicitly completed review; the server wrote coverage.
Available entries = eligible source entries − reviewed entries − entries reserved by other open syncs.
How the collector and frozen pointers work

The collector reads complete JSONL records, remembers read positions, follows the saved active branch and avoids double-counting inherited entries. It omits unsupported content such as thinking blocks and applies best-effort secret removal.

Snapshots retain source pointers, attribution, selected edits and hashes, not copied source text. Later scans cannot silently change their membership or projection. Excerpts are reconstructed from verified originals; missing or changed originals produce an explicit unavailable state, without erasing saved notes, conversations or reference identities. Legacy capped snapshots have a separate explicit expansion operation that preserves earlier notes and citations.

Only explicit review writes sync_coverage. A generation run that started but did not finish successfully blocks review instead of presenting partial work as complete.

Why freeze evidence? A conversation needs a stable meaning. “What did we know in that sync?” should not change merely because the original session grew later.

04

Split the model work.
Not your conversation.

A long history is too large and costly to send in one go. Draken builds smaller summaries with a cheaper model, reconciles them, and gives a stronger model the bounded result.

Save useful partial work

A successful summary is cached under a key made from its input, model, prompt and kind. Retry reuses matching results. Relevant changes produce a different key.

Keep failures bounded

Requests run serially within a tree. Runs have an invocation ceiling. Each summary gets at most one same-model repair. There is no automatic expensive-model fallback.

References are a trail, not a truth stamp.

S1 — one model request[E3] — snapshot evidence[C2] — snapshot context

The model uses short labels; the server maps them to actual sources. A reader can open a cited excerpt. Those labels are local to their request or snapshot, not universal identifiers.

Citation repair and chunk limits

The default Luna path uses larger token-bounded complete batches and one global reconciliation. Other models retain conservative multilevel processing. These are internal processing units, not limits on the whole snapshot; see the canonical summary-pipeline explanation for current budgets.

A summary observation can cite at most 16 distinct references. If the only validation error is the count, the existing second attempt asks the same model to select from that observation’s original references. It does not rewrite the claim, guess IDs, silently take the first 16 or add retries. Other malformed output uses the normal bounded repair.

If validation still fails, the run stops and keeps valid cached work. Shape and source-membership checks cannot prove that an excerpt supports the model’s interpretation.

Why this tree? Large histories become practical to retry without paying to redo every successful step. The cost is information loss; original evidence must remain inspectable.

05

Memory is not
an agreement.

Draken keeps records, summaries and your decisions separate. A model’s suggestion must not become a saved decision just because it was spoken aloud.

Recorded

Conversation

What was asked and generated. Voice records retain generated/interrupted qualifications, not a claim about what you heard.

Derived

Recap

A short model-written reminder. Helps recognize a sync and bring some context into the next one. Not an exact quotation.

Explicitly saved

Your notes

Decisions and carry-forward work that you choose to save through the app’s notes controls.

Recap generation processes the supplied briefing, messages and notes in parts, then combines them. It does not just grab the last few messages. Each final recap is one to five lines, no more than 600 characters.

New discussion or notes make the old recap stale. Closing the call UI requests a refresh; a browser exit cannot guarantee that it happens. You can refresh explicitly. Saved fragments can be reused, and an older frozen input cannot overwrite a newer recap.

Automatic preparation is an explicit policy. When enabled, the combined scheduler may prepare history and paid briefings after enough new eligible work accumulates. It never starts microphone capture or marks evidence reviewed. See automatic preparation, consent and thresholds; browsing alone is not a promise that no background model work is enabled.

Why keep memory small? It makes history easier to browse and avoids resending every previous exchange. The tradeoff is incomplete recall. For detail, go back to the original sync.

06

One voice path:
ChatGPT.

One persistent browser audio connection, through a separate native ChatGPT sign-in and the pinned official Codex helper. No local speech engine, Platform API-key fallback or alternative-provider fallback.

Context is bounded data

The call starts with a briefing, notes and excerpts. Historical lookup uses a fixed prepared cutoff; explicit frozen-source requests retain their snapshot meaning. Evidence travels in acknowledged context parts, separately from the small handoff receipt. Original source roles and dates matter. See retrieval scope and transport limits.

Explicit recall can supply dated history. Prior recaps are labelled as summaries, not quotations. Old requests are not reissued as new instructions.

No path from speech to execution

Tool and approval requests are denied. The helper’s local endpoint can return assistant text, not executable tool calls. It cannot run shell commands, edit projects, save decisions by instruction or advance review.

Malformed endpoint requests are contained, and lookup limits are validated.

30 minMaximum call duration
60User-message limit
90 secDisconnect lease
120Delegated lookups per call

These are resource limits, not a subscription spending guarantee. Only one call can be active; a replacement waits for confirmed helper cleanup. Lookup requests are not the same as spoken turns.

Call controls and conservative history
  • Mute releases microphone tracks. Explicit unmute obtains input again.
  • Speaker-safe mode pauses input during replies. Headphone mode allows full-duplex conversation.
  • Stop reply mutes playback locally and sends a stop request. It cannot prove immediate remote cancellation or the end of accounting.
  • End call cleans up tracks, playback, timers and the connection. There is no automatic reconnection.
  • History stores ordered user and assistant messages, including interruptions. It does not invent exact question–answer pairs, played words, human hearing or agreement.
Experimental interface, not a stable public embedding API. Audio goes to OpenAI. Speech may paraphrase and is not held for complete-answer JSON validation. A successful sign-in or connection handshake alone does not prove usable audio. Quotas, retention and future compatibility are not established.

Why retire the old voice path? Keeping Whisper → pi → Kokoro meant maintaining another working product path the app no longer needed. Its execution code is gone. A small legacy reader preserves old call records without preserving that engine.

07

The dragon
only draws.

The character is a local Three.js scene, not an agent and not a speech engine. It receives read-only playback signals from the call controller.

It can

Animate the character, soften the background, limit rendering work and respect reduced-motion preferences.

It cannot

Capture a microphone, call a model, change notes, start a sync or mark evidence reviewed.

The separate /persona.html app preview uses a stored synthetic sample and approximate text-driven movement. It is for appearance testing, without a live provider call. It is not embedded in this guide.

Why keep it separate? Improving the character should not change microphone permissions or model behavior. A graphics problem should not become a conversation problem.

08

Keep the record.
Not a running action.

Private state lives outside the checkout, by default under ~/.draken/. The main database is ~/.draken/draken.db. Credentials, installed helper files and TLS keys are private runtime material, not application assets.

Survives a server restart

Snapshot membership, pointers, reference identities, saved notes, conversations, review coverage and successful cached summaries. Source excerpts still require their originals.

Recovery follows permission

Calls and foreground work need fresh intent. Enabled automatic preparation may resume owned unfinished batches, but provider failures need explicit retry. The microphone never reopens automatically. See the canonical preparation policy.

Closing a browser page does not cancel an ordinary server-side preparation job. A voice call loses its connection and is cleaned up; page exit cannot guarantee a final recap request. These are different lifetimes.

Transactions keep related writes together: snapshot plus frozen pointers, or completed review plus coverage. Schema changes preserve historical rows, including older tables no longer used by the current app.

Source text and saved conversations have different lifetimes. Losing original logs makes their excerpts unavailable, while notes, conversations and reference identities remain. Draken does not silently substitute copied source text. See the canonical storage contract. Back up current data before deployment; never restore a stale database merely to update code.

Why preserve records but stop actions? A restart should preserve what happened and respect saved preparation permission—not resume audio capture or repeatedly retry provider failures.

09

Convenience is
not permission.

History is untrusted data

A source log may contain “ignore these rules” or an old request to deploy. Reading it does not authorize doing it. Pi processes run tool-free, outside project checkouts, with session persistence and automatic context discovery disabled.

Controls belong on the server

Snapshot locks, review writes, request validation and call ownership are checked by the server. Hiding a button is not an authorization boundary.

Local does not mean offline

Browsing and indexing stay local. Preparation, questions and recaps can send selected text to providers. Native voice sends audio and bounded context to OpenAI.

Cleaning has limits

Obvious secrets are removed on a best-effort basis. Improved outbound cleaning can apply without silently rewriting frozen records. It is not a guarantee that every excerpt is safe to send.

This page and the app have different access rules. This static guide needs no login because it contains no private records or app APIs. The Draken application still requires authentication on the LAN. Microphone capture needs localhost or trusted HTTPS; ordinary loopback app use can work without dashboard login.

Dashboard authentication and provider sign-in are separate. Provider tokens are never sent to the browser. The app rejects cross-origin API requests and protects anonymous loopback use with Host checks.

Why these boundaries? A web page, source-log instruction or generated sentence must not become permission to execute work, expose credentials or declare your review complete.

10

One npm app.
Separate outside needs.

Draken is one npm-distributed application containing its server, built browser UI, persona assets and voice integration scripts. Package consumers do not need a separate frontend install or build.

Server source → runtimesrc/ · TypeScript → compiler → dist/ · Node.js
Browser source → static assetsclient/ · React + TypeScript → Vite → public/ · served by Express
Native integration → direct modulesvoice/realtime/ · JavaScript modules → run directly; official helper installed separately

What runs outside the package?

  • Node.js 22.19 or newer.
  • Configured pi 1.4+ for briefing, text discussion and recaps.
  • The pinned official Codex helper and separate ChatGPT login for voice.
  • Trusted HTTPS for a microphone on the LAN.

Current setup rough edges

One package does not mean every runtime or account is bundled. Voice setup instructions currently use checkout-level commands. The optional synthetic browser probe needs development tooling and a browser; it is not a core voice runtime dependency.

The public website is another thing.

site/ → website deployment workflow → public landing page
client/ → public/ → private local/LAN application
docs/architecture.html → this standalone guide → separate static serving, no app API

The public landing-page artwork is separate from the procedural call dragon. This guide does not publish the website, modify that artwork or change application authentication.

Why separate build output and source? People installing the app need ready-to-run files, not the frontend toolchain. Developers work in source directories; generated dist/ and public/ should not be edited by hand.

12

Check the code.
Keep the caveats.

Tests are evidence about specific behavior, not a certificate that every spoken claim is true or every physical device works.

# Development checkout; run builds and browser tests in sequence.
npm run check    # TypeScript + unused-code checks
npm test         # Server/unit tests with temporary data
npm run test:ui  # Build, then browser workflows

What automated checks cover

Snapshots, review boundaries, caching, citation repair, malformed requests, bounded lookups, denied execution, historical-record preservation, browser controls and no capture on reload.

Ordinary tests use temporary records, fake model/helper responses and local peers carrying synthetic audio. Real-provider checks are separate and explicitly opted in.

What they cannot promise

Complete semantic recall, the truth of every summary, exact words heard, physical microphone and Bluetooth behavior, every mobile browser, subscription accounting, provider retention or future native-interface stability.

A live audio handshake is not proof of a substantive spoken answer. Synthetic peers are not a physical headset test.

TypeScript and Knip help find unused bindings, files and exports. They cannot decide whether a reachable feature belongs in the product. Explicit tests also check that the retired local voice engine stays absent while its old records remain readable.

Not part of this architecture: scheduling jobs, coding workers, project-file edits, deployments or automatic review. Any future execution feature needs its own approval and design; it is not a hidden capability of the voice model.

The central tradeoff: Draken makes a large, scattered history easier to understand. It preserves evidence and your choices, but it does not turn a generated explanation into independent verification.
