# Historical search

**Just ask.** Draken automatically searches retained older sessions, sync conversations and saved notes when you ask a text question or talk to it. The separate **Search history** page (`/history`) lets you inspect the same records directly.

The session activity window defaults to **7 days** and is configurable in **Settings → Agents & sessions**. It controls new indexing, summary preparation and ordinary source search. Older cached work and explicitly opened saved citations remain available; original-byte checks and manual exclusions still apply. See [Session activity window](SOURCES.md#session-activity-window). There is no separate memory-enable switch or search-mode selector. An existing sync offers **Prepare history** when its call history is not ready. Historical retrieval does not replace the complete-snapshot summary tree or advance review coverage.

## Automatic local search preparation

The first request with eligible retained history downloads approximately **136 MB** of pinned model/tokenizer files from Hugging Face, verifies their SHA-256 checksums and prepares local embeddings. Later requests reuse them and automatically embed new or changed records. Empty history does not require a model download.

Search combines meaning and exact keywords every time. It waits for both indexes rather than quietly returning keyword-only results while semantic work is incomplete. First use or a large amount of newly collected history can take minutes. Search, text-reply preparation and pre-call preparation show the current phase, model-download bytes or completed/total **new or changed unique passages**, unchanged cached work separately, elapsed time and an approximate remaining time once enough passages have been measured. The estimate can change with passage length. Progress is read-only metadata; polling it does not start indexing. **Initial calling/chat requires both the briefing and searchable history to be ready.** Later append-only updates do not disable an already-prepared conversation. Sync preparation includes history preparation; an older or changed sync offers **Prepare history**, with progress and cancellation on the sync page, not inside a call. Call creation checks readiness again and rejects unprepared history without starting a call or building an index. Cancelling or failing preparation leaves the microphone off. Ordinary concurrent requests queue behind one history process, within a fixed bound. Its embedding lanes run bounded batches in parallel; they do not run concurrent database writers. An unchanged index shows **History is up to date**, not a full-archive progress bar.

No session text or queries are uploaded for embedding. Text discussion and ChatGPT voice do receive the relevant historical excerpts, just as they receive frozen snapshot context. Those excerpts are dated background—not newly reviewed progress, agreement or permission to execute work.

Opening/reloading a page does not itself download the model, compute embeddings or start a microphone. Source collection happens through sync/scan actions or the optional server-side background schedule below. The search child itself follows only recorded, verified JSONL pointers beneath the configured per-agent source roots; it does not discover sessions or roam project files. There is no automatic decision saving, API-key fallback or second voice engine.

### Optional background indexing

**Settings → Automatically prepare history** controls scanning, local indexing and paid summary caching together. It is on by default for new installations and works while the server runs, even without a browser. Existing installations retain their saved indexing choice, including off; reads and restarts never reset it. On upgrade, an existing `auto_index` choice wins; only when it is absent is the legacy combined preference copied. A missing preference on an existing installation remains off. Retired automatic-briefing consent and job markers are removed, not resumed or migrated into the `auto_summary` preference. Indexing may download the pinned local embedding model on first use and consumes local CPU, memory and disk, but makes no provider model calls. It never creates syncs, summaries, recaps or briefings, starts audio, or advances review. Existing snapshots (including past automatically created ones), cached summaries, conversations and notes remain ordinary retained history, not resumable automatic jobs.

The app's single scheduler checks once a minute. Any positive source-change count or stale readiness can trigger local indexing, including small tails without an active conversation. Connected idle voice permits local background work between turns, but never during a pending response or context delivery. User turns and foreground jobs preempt and drain owned indexing before proceeding. Entries accumulate for the next explicit sync; an indexed backlog never triggers a briefing. Background indexing publishes prepared history for between-turn adoption, not new snapshot membership. A new conversation adopts an already-completed background history receipt without forcing a foreground reindex. If no compatible receipt exists, explicit preparation is still required. New arrivals are included in its briefing snapshot and join archive retrieval after the next completed background pass. An append or scan cursor advance cannot revoke an already-captured valid receipt or disable prepared chat. Metadata hashes detect additions, edits and removals once per original source entry (or discussion/note record). Session/file bookkeeping does not add records, and frozen aliases coalesce with the original rather than multiplying the count. Actual indexing still reconstructs and verifies admitted source bytes. Unchanged checks do not start an embedding request. Source records and embedding passages are different counts. New sessions from enabled agents retain the collector's included-by-default behavior; per-agent/per-session exclusions and the existing baseline remain respected. Codex and Claude sources require separate explicit opt-in in **Settings → Agents & sessions**, even if background indexing is already enabled. Explicit summarization continues to use pi. See [SOURCES.md](SOURCES.md).

Foreground requests preempt and await the owned automatic indexing job. Disabling cancels both stages; explicitly enabling the combined control enables both saved flags and clears the paid failure pause. Completed vectors and valid summary cache remain reusable. Local preparation failures retry no sooner than five minutes; foreground preemption waits at least one minute. **Retry automatic preparation** retries both stages explicitly. Shutdown awaits owned work. Settings/progress GETs remain metadata-only. Home and Settings show local indexing status, pending source changes, entries available for the next sync and the last completed indexing batch—not ownership of a prepared briefing. The shared status exposes paid failure pauses rather than reporting a healthy pipeline after indexing alone; the last summary pass remains a historical count, not current readiness. The saved preference and last completion survive restart.

Only an explicit **Sync with Draken** or **Chat instead** action creates a new snapshot and starts its briefing. It includes all eligible accumulated entries not reserved by another open, non-ended sync, preserving request-ID idempotency and explicit retry. No old automatic snapshot is claimed or resumed by a new request. Preparation usage history still includes past automatic work, retries and failures; indexing does not erase those costs. The hash-only search checkpoint still advances only after successful global preparation. Missing older checkpoints can be established by local preparation, reusing compatible vectors. No source-text copy, provider substitution or vector conversion is introduced.

A failed preparation/search reports an error. If a session file changed, moved or disappeared, scan sessions again before retrying; stale derived text is not a substitute for a verified source. Otherwise retry the question or **Prepare history**; completed embeddings are reused automatically. Cancel preparation on the sync page to stop that work. Cancelling a search or text reply stops its owned work too. Reloading does not start a call. An older cache without a call-readiness record needs one preparation pass, which reuses its compatible vectors. A completed index over a partial import is not sufficient for initial readiness: foreground preparation first drains bounded import chunks to captured file ends. Missing, damaged or incomplete captured originals block readiness. Later appends do not force preparation to chase a live stream forever or invalidate its verified prefix. Each answer uses one prepared cutoff; a newer successfully prepared cutoff becomes eligible between user turns. A ready sync also offers **Refresh history** for an explicit local-only update without regenerating its briefing. See [SOURCES.md](SOURCES.md).

### Live conversations and idle ending

The initial briefing and searchable history must be prepared once. Thereafter, an active text or voice conversation can adopt **newly prepared original history as dated H evidence between user turns**. This is not a moving snapshot: initial membership, E/C references, briefing, already saved transcript and explicit notes are never rewritten by history updates. New H context is not review coverage. Explicit **Mark reviewed** covers only the initial snapshot, subject to its existing evidence/preparation checks.

Each answer/voice turn pins one history cutoff for all its lookups, context parts and any text correction. A completed background pass cannot replace context mid-answer or interrupt a reply. Adoption happens only between turns, never from partially indexed data. Ordinary source appends and background scan/import cursor advances must not invalidate already captured context: the 0.7 file-cursor identity coupling is not a source-integrity check. Keep receipt identity tied to admitted captured records, not mutable tail bookkeeping. Actual damage, missing originals, exclusions or incompatible captured projections still fail closed; reads continue verifying original bytes. If additional archive lookup is unavailable during an update, explicitly qualify unavailable context rather than guess, serve stale derived text or silently fall back to an old conversation. An update alone must not disable already-prepared chat.

Local live updates use only `auto_index`, with once-minute checks for **any positive source changes** while a conversation is active. They do not run per-minute provider calls. `auto_summary` defaults on, preserves explicit opt-outs and has no minimum tail size; its paid-failure policy is below. Neither background path creates syncs, final briefings, recaps, decisions or review. A connected idle voice call is not itself a reason to block local indexing; pending response/context delivery is. A user turn preempts and awaits owned indexing cleanup before retrieval. Settings/status GETs read metadata only: no source-body reads, scans, embeddings or provider inference.

The simple status vocabulary is **Up to date**, **Preparing new info…**, **New info ready**, with **Live updates off** / **Updates unavailable** when applicable. It describes preparation/adoption, not independent verification or guaranteed exhaustive recall. No extra live-update control is required.

Conversation lifetime is separate from review status and native connection limits:

- End after **30 minutes since the last real user chat message or voice turn**. Initial creation counts as initial intent. Assistant responses, polling, indexing, preparation updates and connection heartbeats never extend the deadline. An ongoing reply is allowed to finish before idle expiry; its completion does not reset user activity.
- Persist last activity and an ended marker across restarts using additive conversation fields or a related table. Preserve the existing `open` / `completed` / `discarded` review-status constraint; do not recast idle ending as completed/reviewed. Show **Session ended**.
- An ended conversation cannot accept new chat/voice turns or be revived by request replay, polling, page reopening or restart. Return home and **Start new sync**. Its transcript remains readable, and explicit notes/review can remain available for its old snapshot under existing checks.
- Idle ending releases that conversation's unreviewed reservations for the **next explicit new sync**. It does not delete snapshot rows, create a sync, change notes, generate a recap or advance coverage. Snapshot membership remains historical even after its reservation ends. Unreviewed entries belong in the next snapshot; expiry does not invalidate completed summary batches or existing embeddings. Prior inclusion, successful preparation and explicit review are three different facts.
- Migration derives activity from real stored user turns (creation when none exist), never generated replies or updated-at bookkeeping. Inactive older conversations may end and their unreviewed entries become available again; no history is deleted.
- Voice's separate **30-minute connection limit, 60-turn cap and 90-second disconnect lease** may still end a connection earlier. The user-idle policy is not removal of resource bounds or a promise of unlimited calls.

### Automatic summary preparation

**Settings → Automatically prepare history** controls both saved flags (`auto_index`, `auto_summary`), defaulting on and using the configured summary provider's quota/API billing. Reads and upgrades preserve existing opt-outs and failure pauses; legacy indexing-only consent stays local-only until explicitly enabling the combined control. Settings/progress GETs are metadata-only and start no work.

The sync page distinguishes newly included entries from unreviewed entries carried forward from earlier snapshots. These are membership counts, **not** a count of provider requests or proof that preparation completed. Reusable summaries and physical embedding vectors are independent of conversation expiry and review. New snapshot aliases may need metadata links, and originals still need verification; neither authorizes regenerating unchanged corpus embeddings or silently repeating completed provider work.

#### Read-only eligibility, shared summary cache

Paid preparation reads the accumulated entries eligible for the next explicit snapshot, respecting enabled agents, session selection, the activity window, baseline, active-branch projection, verified originals, existing coverage and entries reserved by open, non-ended syncs. It does not reserve those entries or create/own `syncs`, `sync_items`, `sync_coverage`, `sync_messages`, `sync_runs` or `sync_tree_nodes` rows. It never runs the final model, generates a briefing or recap, starts a call, saves user notes or advances review. Existing histories, notes, coverage and frozen snapshots are unchanged.

The work warms the **same validated `summary_cache` leaves plus reconciliation/compact final input used by explicit sync**, with the same model/prompt/content identity and citation validation—not a separate rolling-memory summary or an unvalidated text shortcut. An explicit sync freezes all then-eligible accumulated evidence and consumes matching cache; warming cache is neither inclusion nor review. Completed batches retain their original input boundaries across appends and combined snapshots, including a completed partial tail and successful work from a cancelled run. Only uncovered or changed input needs new leaf preparation; a previously included entry without a successful cached result still needs its first preparation. Aggregate reconciliation for a different combined input may need on-demand work at **Start chat**; the final briefing and any prior-conversation recaps always remain explicit. Cache preparation can reduce repeated work, but does not promise zero latency.

#### Scheduling, ownership and recovery

- The scheduler checks **once a minute while idle** and prepares eligible new or changed input, including single-entry tails. Summary receipts are independent of the embedding checkpoint: local indexing cannot consume the summary backlog.
- An unchanged successfully prepared input with intact cached outputs causes **no further provider calls**. Receipts include hashes of every validated leaf and parent used by the build. Lost or corrupt outputs invalidate the receipt and permit a bounded rebuild; failures still pause paid retries. Eligibility/input hashes, rather than elapsed time or embedding progress, identify paid work and reuse. Edits count once per stable agent/session/entry identity; removals count too. Derived session titles are presentation metadata, not a change to every record in the session. Model, recipe or context changes can invalidate preparation even without new entries.
- Use only the configured summary model and the same configured **`max_invocations`** allowance. Repairs consume that allowance. There is no provider/model fallback and no final-model call. This is an invocation bound, not a token/dollar or subscription-quota guarantee.
- Foreground work **cancels and awaits owned background provider work** before proceeding. Shutdown also drains owned work. A cancellation request is not confirmation that the child/provider process exited.
- Valid completed cache survives cancellation and restart. Resuming the same interrupted input retains spent invocations rather than resetting the allowance. An interrupted request may have incurred provider usage even if no reusable result was saved.
- **Paid failures pause retries until explicit retry.** A timer, restart or additional source activity must not turn failure into an unattended paid retry loop. Local indexing failures retain their independent delay of at least **five minutes**.
- Disabling the combined setting stops both stages; completed cache and spent invocation counts remain. A successful receipt describes the captured batch, so later arrivals do not discard it. Summary preparation assumes append-only records: reuse completed input receipts and recheck current agent/session consent, rather than reopening all original dependencies at every node and publication boundary. Selected citation/retrieval reads still verify original bytes.

#### Durable metadata and usage

The additive **`background_runs`** table stores durable input/cache hashes, invocation counters, state, content-free request metrics and timestamped failed-attempt events. Cancellation between successful provider calls still counts as an interrupted attempt; resuming the same run must not erase it or count it twice. It stores **no source text**, prompts or source excerpts; validated derived summaries belong in `summary_cache`. Persistence distinguishes prepared, interrupted and failed work across restarts without manufacturing a snapshot. Original logs remain authoritative. Status reports the **last successful background pass**, not live readiness: it reads only counters/timestamps and never reopens transcripts or validates the cache during polling. Actual preparation and explicit syncs verify originals and cached outputs.

Ordinary existing batch keys and validated historical leaf caches remain compatible. Previously oversized batches split at a moving midpoint may need one-time recomputation: 0.7 uses stable prefixes so future appends do not move completed boundaries. No old cache or snapshot is deleted as part of this change.

**`preparationUsage` includes background spend, requests and failures**, alongside explicit preparation and retained historical accounting. Missing/interrupted pricing remains unavailable or partial, never fabricated zero. **`completed_batches` still counts explicit snapshots' first successful briefings**, not warmed chunks or background runs; repeated preparation does not make another reviewed/completed sync. Background cost must not be silently assigned to a later snapshot as though its cache hit made a new request. Opening the usage dashboard only reads metadata. Chat, voice, standalone post-conversation recaps and local resource costs remain outside this preparation-only estimate.

## Work questions and follow-ups

Voice and **Chat instead** use the same model-based search planning inside `src/evidence`. The configured summary model receives the actual question, up to six earlier user turns, the briefing as untrusted context, and currently permitted session metadata. It chooses a search query, relevant sessions, original work versus conversation (or both), and whether to include recent records. Callers do not infer status, project switches, recall or follow-ups with regexes or word lists. Model interpretation can still be wrong.

Local retrieval alternates keyword and vector result lists, plus recent records for current-status questions. It skips duplicate originals before advancing to the next list. There are no role, age or keyword score bonuses and no separate assistant-only search. The model's query resolves follow-ups and covers the requested topics. Recent records are included when the model requests them, including last/previous-discussion questions, not when a particular word matches a regex. All candidates must meet source permissions, project scope and the prepared cutoff. Useful negative or historical evidence is not confirmation of a current defect.

Voice uses the same summarization-model evidence selector as text chat: up to 64 candidates, up to eight selected originals plus nearby messages, and a 32,000-byte historical packet. The existing native voice model answers; there is no extra text-answer call. An explicit E/C status question also carries its requested frozen excerpt (up to 3,500 bytes, combined envelope at most 36,000 bytes); it no longer bypasses archive update checking. Frozen source session/sequence metadata permits comparison with historical aliases without inferring chronology across sessions. Excerpts keep contiguous text, including tool requests, and retain closing qualifications when shortened. A later passage can include its source's beginning for context. Native context appends remain bounded to 8,192 UTF-8 bytes: a larger evidence document travels losslessly as ordered, JSON-quoted fragments followed by a completion record, not a truncated handoff or another model-generated summary. There are at most twelve fragments plus one completion record; transport quoting adds overhead to the selection budget. Sources are published and continuation becomes eligible only after complete delivery. A failed transfer ends the call; Stop/new turns prevent further old fragments, completion and continuation. The helper's small handoff response carries only a completion receipt after the full context has been delivered.

New calls pass actual prior user turns to the same planning step as chat. Generated replies and native search hints are not authoritative instructions or hard project restrictions. The helper can refine a question or request an H reference (optionally with `offset 2000`); each user turn permits at most three distinct archive lookups and reuses both duplicate results and their delivery. Source IDs are supplied context for that turn, not verified per-claim citations or evidence of hearing/agreement. A failed or empty work lookup is not silently replaced by an old conversation. Each distinct voice lookup makes one pi planning/scope call, then one selection call for project requests, even with no candidates. Unrelated or unclear requests stop after planning without archive search. Duplicate lookups reuse their result; at most three distinct lookups share the configured invocation allowance for that user turn. Stop, a new question and ending the call cancel planning and selection. Invalid planning or selection stops further lookups for that turn and supplies an explicit lookup failure. Durable invocation/usage records survive restart without becoming text-chat retry jobs. The spoken-answer target is unchanged.

### Separate text chat

Text and voice use the internal `src/evidence` module through one public entry point. Project-related advice, opinions and technical explanations are allowed: cite the recorded facts behind them and distinguish recommendations from agreed decisions. Clearly unrelated requests get a short scope message, not a general-purpose answer. Unclear requests get a clarification question. Relevance depends on conversation context, not keywords or the presence of search matches. Text scope messages need no answer-model call or historical citations; voice delivers the same decision through its native answering model. Failed prepared search stops the text reply rather than inventing a scope decision or silently choosing another search mode. Model scope decisions can still be wrong.

Chat has its own short-answer style rather than the opening briefing's headings: normally one paragraph or up to three bullets, targeting 60–100 words excluding citations, with shorter answers for simple questions and more detail only when requested. The same style is retained during a citation-label correction. This does not reduce evidence selection, remove necessary qualifications, truncate a generated reply to a word count, or add another model request. Actual provider adherence is not guaranteed by synthetic prompt-contract tests.

`/syncs/:id/chat` uses the shared model planner, prepared-only source search, and model selection step. The module has no external imports; the host injects metadata listing, search, verified reads and text cleaning. Planning cannot change the pinned cutoff, permissions, or an explicit host restriction. The final historical packet is at most 32,000 UTF-8 bytes and 24 sources, including nearby messages. Recent actual user questions in the sync's saved chat and native call transcripts establish follow-up scope; assistant replies cannot select a project. The text model receives qualified recent call transcripts as context, not evidence of hearing or agreement. Source-reference validation checks existence, not per-claim truth.

Local search gathers up to **64 candidates**. The configured summarization model sees an 800-character excerpt from each, source dates, roles, session/order, and up to six recent user messages. Later passages can also carry a 400-character opening excerpt. It also sees up to 4,000 briefing characters plus a truncation marker. It returns a project-relevance decision and up to eight candidate IDs, not an intermediate answer. The final model receives reread originals plus their immediate neighboring messages, which can connect a command to its result or a response to its request. Source checks and the turn's cutoff apply again after selection. Sequence orders records within one session, not across sessions.

A normal project text turn uses **three model calls**: planning, selection and answer. All use the existing invocation allowance, provider and cancellation path. Planning and selection reserve one invocation for the answer. The existing citation correction can make four calls. Scope refusals use just the planning call, without an answer or repair call. This adds one model request and its latency/cost compared with selection-only retrieval. An empty candidate set still needs a relevance decision; an empty selection is allowed and is not proof of absence. Invalid plans, unknown or repeated IDs stop the message before the answer call, with no automatic retry or fallback model. Standalone local search does not add a selector call. Voice uses this same selector, with its existing native voice model providing the answer.

Packets retain contiguous excerpts and separately labelled ending excerpts with original offsets when shortened, including shortening to meet the byte limit. Omitted matches are disclosed. The selector cannot recover a record outside its candidate pool, and it can make bad choices within that pool. This is not exhaustive archive verification.

Final answers use a stable per-request `R1`, `R2`, … label catalog, mapped by Draken to the admitted E/C/H source references before validation and persistence. Source excerpts, earlier briefings and discussion are quoted data: their embedded citation syntax does not create labels. Explicit source requests are mapped into the same catalog. Unknown labels are neither guessed nor dropped. Missing/out-of-catalog citations permit **one correction using the same final model and invocation/cancellation budget**. A second citation failure retains the user question without saving an invalid answer. **Checking source references** identifies this stage. The citation correction can consume one additional final-model request; chat/repair usage remains outside the preparation-only estimate. This citation-consistency check is not proof that every claim is true. Native voice shares model-based selection, but **not the pi answer-repair pass**: already-streamed speech cannot be retracted or certified by this citation check. Its prompt keeps the same concise delivery target, including necessary caveats. Shared evidence does not establish identical generated answers or exhaustive recall.

Chat and voice pin a recorded prepared cutoff per turn and adopt newer prepared history only between turns. After initial preparation, text chat uses the saved briefing and recent conversation without rebuilding the summary tree, reopening the entire frozen snapshot or revalidating the whole history receipt. Prepared search ranks cached candidates first and resolves only selected originals; explicit E/C requests read at most three requested frozen excerpts. Selected evidence still requires current source permission, matching original bytes and prepared passages. Unrelated missing or unprepared records do not veto chat. All sync HTTP responses omit original evidence bodies, including initial loads, preparation completion, mutation results and retries. The bulk evidence browser is removed; a citation fetches only its frozen original in 4,000-character pages, checking current source permission and bytes. Opening a page does not resolve originals. Internal briefing/review operations still obtain the evidence they need. Local background preparation or an explicit refresh can publish a newer cutoff; neither regenerates the briefing or switches providers.

## How it works

```text
Canonical metadata in draken.db (read-only to search worker)
             │
             ├── selected session pointers → verified JSONL records
             ├── frozen evidence pointers → exact recorded JSONL/edit selections
             ├── preserved sync discussion (with playback qualifications)
             └── explicitly saved notes
             ↓
Automatic local preparation when needed
             ├── SQLite FTS5 word index
             └── sqlite-vec over local text embeddings
             ↓
Combine matches → bounded source/context reads → dated H citations
```

- **Model:** `Xenova/multilingual-e5-small`, pinned revision `761b726dd34fb83930e26aab4e9ac3899aa1fa78`, quantized ONNX. Uses query/passage prefixes, mean pooling and normalized 384-dimensional vectors. Long token sequences use bounded windows rather than silently embedding only a prefix.
- **Runtime:** CPU WASM through the same pinned `onnxruntime-web`, in one server-side history process. On machines with at least 12 available logical CPUs and 4 GiB of available memory, deltas of at least 32 passages use up to two isolated embedding worker threads, each with one model session and three kernel threads (six total). Smaller/constrained machines keep one lane, with at most four kernel threads and half the available CPUs (minimum one). Reads start no model; queries/small deltas use one lane. A second in-memory model copy costs additional RAM (about 1.7 GB process RSS for two lanes versus roughly 1 GB previously on the qualified host), but adds no on-disk model copies, GPU package or runtime dependency. Lanes retire with the history process, including cancellation; failures stop the request rather than switching runtimes. It is **not imported by the client** and is not transcription or speech synthesis. This avoids native CUDA-install downloads. The runtime package itself occupies additional disk space (about 133 MiB in the qualified Linux install), beyond model files.
- **Tokenizer:** pinned `@huggingface/tokenizers`; no downloaded executable model code.
- **Search:** FTS5/BM25 plus pinned `sqlite-vec` 0.1.9. Approximately 800-character overlapping passages (without redundant short tails already covered by the preceding passage), up to 80 candidate chunks per method. Results alternate between lists without weighted score mixing. Direct lookups default to eight originals; text chat requests up to 64 candidates for model selection. The minimum cosine-similarity threshold is a heuristic, not a correctness guarantee. Exact identifiers remain important keyword matches.
- **Identity:** content-addressed `H…` references retain source attribution; snapshot-local E/C labels are not global IDs. Duplicate attributions retain scope membership while sharing embeddings and collapsing in results. Changed/excluded records cannot silently replace the text behind an old link.
- **Preparation:** source admission and raw pointer integrity are still revalidated; delta indexing does not skip those checks. A bounded, process-local normalization cache avoids reparsing unchanged records, but is consulted only after rereading and verifying the complete raw-record hash. No cached text substitutes for missing or changed originals, and this cache is never written to disk. Only added/changed/deleted source records update postings and links. Only unique passages without a compatible vector enter the embedding queue. Unchanged refreshes perform no index writes, and a fully cached preparation does not load/download a model; an actual semantic query still ensures its model is ready. At most eight passage inputs are scheduled per batch, with no unbounded queue. Writes commit at batch boundaries after at most 64 passages or roughly a second of computed work. Progress counts only committed delta passages from zero; cached counts sit outside the denominator. A retry counts only work still uncommitted. ETA measures parallel wall-clock throughput and excludes the first cold batch. The existing model fingerprint/cache and original source references remain valid; obsolete fully covered tail chunks are removed only from the derived index.
- **Bounds:** one worker and at most eight queued requests; bounded queries, candidates, source pages and context packets. Preparation/search stops after ten minutes without a progress update, or two hours overall; read operations retain their 30-second limit. A healthy first index is no longer killed merely because it passes 30 minutes. The separate voice-call limit still applies. The worker retires after five idle minutes. Cancellation terminates the owned child when needed; queued work waits for its exit before starting a replacement. Search/read cancellation is isolated from other queued requests. Server shutdown cancels all owned work.
- **Storage:** `records` retains attribution metadata, not another full-text copy. Unique `passages` hold input hashes and embedding state, not text; `chunk_links` retain every source occurrence and offset. `passage_vectors` stores one vector per unique input. `chunks` and `embedding_cache` are join views, not duplicate physical stores. Contentless FTS5 keeps occurrence-level token postings and positions, not original passage strings, so scope membership and keyword document frequencies remain intact. Tokens and vectors are still private derived data, not an anonymization or secure-erasure mechanism. Text for reads and embedding is reconstructed from verified sources in memory. Semantic ranking selects scoped unique passages, expands their scoped occurrences, then bounds the candidate list; ties can rank differently from the former per-occurrence vector layout.
- **Rebuildability:** the separate passages, keyword index and vectors are derived. Fingerprints invalidate incompatible model data. The worker opens `draken.db` read-only and can read only recorded session files beneath the explicitly supplied session root. It has no source-file write, discovery, scan or application-write path.

## Pointer storage and migration

Live `agent_entries` keep metadata, agent/session attribution, parser versions, byte offsets/lengths, raw-record SHA-256 hashes and branch/edit links—not `text`, `effective_text` and replacement copies. Reads verify the configured root, regular-file identity, session header, complete record hash and normalized entry identity. Context edits resolve both the original record and the selected edit. Append scans verify prior pointers when the file changes, including middle rewrites that leave its prefix and old tail intact.

**Pi JSONL files are the authoritative original-text archive, including for old snapshots.** `sync_items` and frozen background context pin the original record coordinates/hash, normalization version, exact selected context-edit pointer when present, any historical excerpt-clipping recipe, and a projected-text hash. Their membership, attribution and E/C identities remain frozen; later appends/edits/branch switches do not redirect them to the live projection. The current schema has no `retained_text` table. Versioned normalization reproduces older evidence exactly while current model-facing redaction remains in force.

Missing or altered originals are explicitly unavailable, not substituted with search text. Snapshot pages still show discussion, notes and stable citation identities. Generating replies, calling, expanding or marking the snapshot reviewed requires its evidence to be available. Restore the original files and rescan if live pointers moved or their file identity changed. Frozen reads can follow a newly registered path only after checking the session, record hashes and projection. An explicit scan updates current missing/admission state; it does not reconstruct lost snapshot bodies.

The one-way `pointer-v2` migration verifies every existing body against recorded original session prefixes before removing it. Unavailable, ambiguous or unmatchable originals stop and roll back conversion, preserving the old database rather than deleting or guessing evidence. Legacy edit matches must be unique, on a descendant branch and not dated after the snapshot; they carry `legacy_edit_match` because exact edit selection was not originally recorded. New snapshots record that selection directly. Entry IDs, projected evidence, notes, review coverage and summary caches are preserved. The `history-index-v3-contentless` search migration removes passage-body storage while retaining compatible vector bytes, occurrence/reference IDs and keyword frequencies without inference or an embedding-model change. Each database's conversion is transactional and can retry after failure. Unknown formats or conflicting vectors fail visibly instead of silently rebuilding.

Back up both current databases before deployment and qualify migration on private copies. Older binaries are not compatible with the pointer schema. SQLite can retain freed pages and WAL files: reclaiming them with an offline checkpoint/VACUUM is a separate deployment step, not automatic history deletion or page-open maintenance. The search worker closes SQLite on orderly retirement and requests a 4 MiB retained-journal limit after normal checkpoints; active transactions/readers can still require a larger WAL. Backups and pinned model files are additional disk use and are not included in compacted database-size claims. Pre-migration rollback backups still contain the old copied text; migration does not delete or securely erase those backups.

## Scope and qualifications

Source inclusion, missing-session state, active branches for unsnapshotted entries and the existing history baseline are respected. Frozen evidence remains historical, including superseded branch material. Reviewed records remain searchable. Discarded sync discussion/notes are excluded, while discarded work can still be eligible through an active selected session.

Standalone search can prepare candidates observed at its start; text discussion requires the briefing and history to be prepared first. Active chat and voice instead pin a prepared history cutoff for each answer/turn: retrieval verifies original bytes and queries existing passages, but does not build missing corpus embeddings or download a missing model in a pending reply. Newer records wait for successful local preparation and a between-turn boundary, not necessarily a new call. Query embeddings still run locally during a call. Exclusions and edits are rechecked after inference; damaged or unprepared history is not silently substituted or rebuilt inside the answer. If extra archive lookup is unavailable during an update, disclose the limitation. This avoids mixing fresh keyword-only records into results described as fully hybrid.

Sync discussion is its own retained record: excluding a session does not erase text previously discussed in a sync. Recaps/current briefings are not separately indexed as primary evidence, though preserved discussion can contain historical assistant summaries; attribution remains visible.

Search covers admitted normalized source projections and retained Draken discussion—not every byte of the original JSONL files. Excerpt, ranking and packet limits can omit important information. No match is not proof something never happened. Similarity is not proof a source supports an answer. The local multilingual qualification is not a comprehensive relevance benchmark.

Open-sync notes have no retained edit timestamp and are not backdated. Date filters exclude undated notes. Each voice turn pins its adopted prepared-history cutoff; work questions continue preferring original agent records rather than retrieving the active conversation's own questions as evidence. A date filter does not reconstruct an earlier database state: context edits may change retained text without supplying a separate edit date.

Generated/interrupted speech stays qualified as generated/interrupted. Historical requests are data, not instructions. Prompts distinguish plans, reported work, observed validation and uncertainty. Models can still make semantic mistakes; inspect supporting records. Retrieval cannot save decisions, execute tools, complete syncs or advance coverage.

## Private files and packaging

Under `DRAKEN_DATA_DIR` (default `~/.draken`):

- `draken.db`: canonical live/frozen pointers and metadata, Draken conversations, notes and generated summaries; not rewritten by retrieval. Paid preparation writes validated `summary_cache` and metadata-only `background_runs`, never snapshot/review/conversation rows.
- `memory/index.sqlite` and sidecars: passage hashes/unique vectors, source-occurrence mappings and contentless keyword postings.
- `memory/model/`: three pinned model/tokenizer files, downloaded automatically when first needed.

The directory is private (0700); database/model files are 0600. Embeddings are private data too. None belongs in a commit or npm tarball. Exclusions remove queryable derived records/cache on refresh; this is **not secure erasure** of filesystem blocks, WAL files, backups or canonical snapshots.

The npm package contains code/dependencies, not downloaded weights or private indexes. No database service, extra account, GPU package or user-selected search backend is required. Extension/model/runtime failures are visible; there is no alternate provider or keyword-only fallback.

## Checks

Ordinary tests use synthetic records and deterministic or empty embedding fixtures, with real FTS5/vector tests. They do not download/run the real model. Browser fixtures exercise automatic search and source reading without setup controls, plus no capture on navigation. Existing native-only and review-boundary tests remain.

Optional real-model qualification and CPU comparison commands live in [CONTRIBUTING.md](CONTRIBUTING.md#local-model-qualification). Those are isolated test tools, not steps required to use search. Search and text requests prepare the index automatically; calls require completed preparation first. There is no separate model setup command for users.

Synthetic retrieval and throughput checks do not establish exhaustive recall, real-provider answer quality or performance on every machine.
